حلقه عامل The Agent Loop

  • ابزارها: خواندن/جستجوی فایل، ویرایش، ترمینال، تست، مرورگر، MCP
  • مشاهده: خروجی build، خطای تست، lint
  • حلقه تا رسیدن به هدف یا توقف تکرار می‌شود
  • بدون معیار «موفقیت» قابل‌اندازه‌گیری، عامل خودش به خودش نمره می‌دهد!
عامل در یک حلقه کار می‌کند: هدف را می‌گیرد، برنامه می‌ریزد، ابزار اجرا می‌کند، نتیجه را می‌بیند و تکرار می‌کند. مهم‌ترین نکته: باید یک سیگنال قطعی مثل تست داشته باشد؛ ارزیابی خود مدل از «تمام شد» کم‌اعتمادترین سیگنال است.

مهار عامل: راهنماها و حسگرها Harness: Guides & Sensors

از مقاله Harness Engineering در martinfowler.com: هدف این است که احتمال درست انجام دادن بار اول بالا برود و یک حلقه بازخورد خودکار خطاها را قبل از رسیدن به انسان بگیرد. راهنماها قبل از عمل، حسگرها بعد از عمل.

چهار artifact که نباید قاطی شوند

اشتباه شماره ۱ تیم‌ها: کپی کردن کل BRD داخل فایل Rule.

این مهم‌ترین اسلاید ارائه است. اگر فقط یک چیز یادتان بماند: Spec برای یک فیچر است، Rule دائمی است، Skill یک رویه است، و مستندات کسب‌وکار ماده خام است نه پیکربندی عامل.

Spec چیست؟ Specification

توصیف یک فیچر یا تغییر مشخص: هدف، داستان کاربر، معیار پذیرش، خارج از محدوده، لبه‌ها.

  • عمر: برای یک فیچر/تسک (در حالت spec-anchored نگه داشته می‌شود)
  • کی بارگذاری می‌شود: فقط وقتی روی همان فیچر کار می‌شود
  • نویسنده: PO + Tech Lead
  • مصرف‌کننده: عامل توسعه، Developer، Tester
  • محل: specs/001-feature/spec.md

مثال جمله Spec

«Given قسطی با بیش از ۳۰ روز تأخیر، When لیست پیگیری درخواست شود، Then آن قسط با برچسب Overdue نمایش داده شود.»

قابل تست ✓ · مختص این فیچر ✓

Spec قرارداد بین کسب‌وکار، فنی و عامل است. معیار پذیرش باید قابل تست باشد؛ همین معیارها بعداً حسگرهای عامل می‌شوند.

Rule چیست؟ Rules / Instructions

سیاست دائمی پروژه که عامل در تقریباً هر ویرایش مرتبط باید رعایت کند.

  • مرزهای معماری (Clean Architecture)
  • نام‌گذاری و ساختار پوشه
  • حداقل‌های تست، امنیت، دستورهای build
  • محل: AGENTS.md، .cursor/rules/*.mdc، CLAUDE.md، .github/copilot-instructions.md
  • مالک: Tech Lead — مثل کد review شود

مثال Rule

- Domain must not reference Infrastructure.
- Money fields use decimal, never double.
- Never hardcode secrets.
- Run: dotnet build && dotnet test

دائمی ✓ · کوتاه و دستوری ✓

Rule ها همیشه یا با glob بارگذاری می‌شوند؛ پس هر کلمه اضافه هزینه context دارد. کوتاه، دستوری، و دائمی بنویسید.

Skill چیست؟ Agent Skills (agentskills.io)

یک رویه قابل‌استفاده مجدد که عامل فقط وقتی لازم است بارگذاری می‌کند. استاندارد باز (اصالتاً از Anthropic) که Cursor، Claude Code، Copilot و Codex پشتیبانی می‌کنند.

.agents/skills/dotnet-cqrs-feature/
  SKILL.md        # name + description + steps
  references/     # optional docs
  scripts/        # optional helpers
  assets/         # optional templates

Progressive Disclosure

نکته کلیدی Skill: بارگذاری تدریجی. عامل در شروع فقط نام و توضیح همه Skill ها را می‌بیند؛ وقتی کار مرتبط بود کل متن را می‌خواند. پس می‌توانید ده‌ها Skill داشته باشید بدون شلوغ کردن context. فیلد description همه بار trigger را به دوش می‌کشد.

Business Doc — و چرا «قانون کسب‌وکار» ≠ Rule عامل

مستندات کسب‌وکار = دانش دامنه برای انسان‌ها (و گاهی عامل): واژه‌نامه، روایت فرایند، BRD، نقشه فرایند.

به‌طور خودکار بارگذاری نمی‌شود؛ از Spec به آن لینک بدهید یا خلاصه‌اش را در Skill/references بگذارید.

محل پیشنهادی: docs/domain/glossary.md، docs/domain/installments.md

قانون کسب‌وکار: «اقساط معوق بیش از ۳۰ روز باید پیگیری شوند»

  • ✓ در مستند دامنه (حقیقت برای انسان)
  • ✓ در Spec فیچر مربوطه، به‌شکل معیار پذیرش
  • ✓ اختیاری: در references یک Skill اگر مکرر لازم است
  • ✗ در .cursor/rules — مگر قرارداد دائمی کدنویسی باشد
این سؤال را زیاد می‌پرسند: «قوانین کسب‌وکار ما Rule هستند یا Skill؟» جواب: معمولاً هیچ‌کدام! جای آن‌ها در مستندات دامنه و Spec است. Rule عامل یعنی قرارداد کدنویسی، مثل «پول همیشه decimal».

درخت تصمیم: این متن را کجا بگذارم؟

این درخت را در پوشه samples/templates هم گذاشته‌ام. سه سؤال: آیا فقط برای این فیچر است؟ آیا قرارداد دائمی است؟ آیا رویه تکراری است؟ اگر هیچ‌کدام، مستند کسب‌وکار باقی بماند و از Spec به آن لینک بدهید.

MCP، Subagent و Hook

MCP

Model Context Protocol — پروتکل استاندارد اتصال عامل به سیستم‌های بیرونی.

Jira، GitLab، دیتابیس، مستندات، مرورگر

Subagent

عامل کمکی با context جدا و ابزار محدود؛ فقط خلاصه برمی‌گرداند.

تحقیق کدبیس، بازبینی read-only، تست

Hook

اسکریپت قطعی در رویدادهای عامل (قبل/بعد ابزار، پایان).

«Rule توصیه است؛ Hook تضمین است.»

مثال: بعد از هر ویرایش فایل .cs ← Hook اجرای dotnet build؛ قبل از commit ← subagent بازبین.

Anthropic می‌گوید CLAUDE.md توصیه‌ای است ولی Hook قطعی است. چیزهایی که حتماً باید اتفاق بیفتد را Hook کنید. Subagent ها context اصلی را تمیز نگه می‌دارند.

چرا Spec؟ Vibe Coding در برابر کار ساختاریافته

Vibe Coding

  • پرامپت ← کد ← امید!
  • عامل «چیز اشتباهی» را درست می‌سازد
  • هیچ معیار پذیرشی برای بازبینی نیست
  • دانش در تاریخچه چت گم می‌شود
  • برای نمونه اولیه خوب؛ برای محصول پرریسک

Spec-Driven

  • نیازمندی ← Spec ← Plan ← Tasks ← کد
  • هم‌راستایی PO و فنی قبل از مصرف توکن
  • معیار پذیرش = حسگر عامل
  • Spec در ریپو می‌ماند و نسخه‌بندی می‌شود
  • بازبینی در برابر Spec، نه حافظه

DX / Laura Tacho: مشکل اصلی تیم‌ها «هم‌راستایی» است — SDD تلاشی برای حل همین است.

در پادکست Thoughtworks، Birgitta Böckeler و Laura Tacho می‌گویند ارزش اصلی SDD هم‌راستایی است: قبل از اینکه عامل شروع کند، همه درباره «چه» توافق داشته باشند.

سه سطح SDD از نگاه Birgitta Böckeler martinfowler.com

۱. Spec-first

Spec خوب اول نوشته می‌شود و برای همین تسک استفاده می‌شود؛ بعد از تسک ممکن است کنار گذاشته شود.

۲. Spec-anchored

Spec بعد از اتمام تسک نگه داشته می‌شود و برای تکامل و نگهداری همان فیچر استفاده می‌شود.

۳. Spec-as-source

فقط Spec توسط انسان ویرایش می‌شود؛ کد تولیدی است و دستی ویرایش نمی‌شود. (هنوز آزمایشی)

منبع: “Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl” — Birgitta Böckeler، martinfowler.com

Böckeler این سه اصطلاح را خودش ساخته تا آشفتگی بازار را مرتب کند. پیشنهاد من برای تیم ما: برای فیچرهای مهم حداقل spec-anchored؛ یعنی Spec را بعد از merge دور نریزیم و به‌روز نگه داریم.

جریان Spec Kit github/spec-kit

چک‌لیست کیفیت

  • ☐ اندازه یک PR یا اپیک کوتاه

قالب کامل در samples/templates/WRITE-A-SPEC.md است. مهم‌ترین بخش معیار پذیرش است؛ اگر نتوانید برایش تست بنویسید، معیار مبهم است. Non-goals هم خیلی مهم است چون عامل‌ها تمایل دارند کار اضافه انجام دهند.

نمونه واقعی Spec — پیگیری اقساط معوق

هدف: فروشنده اقساط معوق را شناسایی و اقدام پیگیری ثبت کند تا وضعیت شفاف شود.

معیار پذیرش:

  1. Given قسط با بیش از ۳۰ روز تأخیر، When لیست درخواست شود، Then با برچسب Overdue بیاید.
  2. Given قسط معوق، When پیگیری ثبت شود، Then رکورد با CreatedAt و CreatedBy ذخیره شود.
  3. Given پیگیری‌ها، When جزئیات خوانده شود، Then تاریخچه جدید به قدیم برگردد.
  4. Given ورودی نامعتبر، When ثبت شود، Then خطای اعتبارسنجی/NotFound و هیچ ذخیره‌ای.

خارج از محدوده: ارسال خودکار پیامک، محاسبه جریمه، UI وب.

قانون دامنه (از docs): هر اقدام پیگیری باید قابل ممیزی باشد.

این Spec الهام‌گرفته از فیچر follow-up در agent.portal است. ببینید که قانون کسب‌وکار ۳۰ روز اینجا به شکل معیار پذیرش آمده، نه در Rule.

چگونه Rule خوب بنویسیم

  • ✓ خوب:
  • کوتاه، دستوری: Do / Don't
  • دائمی، نه مخصوص یک تیکت
  • با globs محدود شود
  • چند فایل کوچک بهتر از یک فایل غول
  • ✗ بد:
  • مقاله بلند / آموزش گام‌به‌گام (← Skill)
  • دستور مخصوص یک فیچر (← Spec)
  • کپی BRD (← docs)
.cursor/rules/dotnet-clean-architecture.mdc 
---
description: Clean Architecture boundaries
globs: "**/*.{cs,csproj}"
alwaysApply: false
---
# .NET Clean Architecture
## Do
- Depend inward: Host → Application → Domain
- Business rules in Domain/Application
- Use Result for expected failures
## Don't
- Reference Infrastructure from Domain
- Use DbContext in controllers
- Invent folder layouts without an ADR
فرمت mdc در Cursor تنها فرمتی است که برای هر Rule فعال‌سازی جدا دارد: همیشه، با glob، یا وقتی عامل لازم بداند. فایل قدیمی cursorrules منسوخ شده.

چگونه Skill خوب بنویسیم

  • name: کوچک، با خط تیره، هم‌نام پوشه
  • description: چه می‌کند + کی فعال شود (تمام بار trigger)
  • بدنه: مراحل شماره‌دار، دستور دقیق، چک‌لیست خروجی
  • زیر ~۵۰۰۰ توکن؛ اضافه‌ها در references/
  • با یک کار واقعی تیم تست شود
  • رویه تکراری باشد، نه فیچر یک‌باره

---
name: dotnet-cqrs-feature
description: Add a MediatR CQRS feature (Command/Query,
  Handler, Validator, Controller). Use when the user asks
  to add a new API feature, use-case, command, or query.

## Steps
1. Read specs/**/spec.md (acceptance criteria)
2. Application: Command/Query + Handler + Validator
3. Infrastructure: repository methods if missing
4. Host: thin controller → MediatR
5. Tests: happy path + validation failure

## Output checklist

- [ ] Spec acceptance criteria covered
ببینید Skill به Spec ارجاع می‌دهد: مرحله اول «Spec را بخوان». این‌طوری سه artifact با هم کار می‌کنند: Spec می‌گوید چه، Skill می‌گوید چطور، Rule مرزها را نگه می‌دارد.

دام‌ها و نقدها

⚠️ اصطلاحات هنوز سیال است

Böckeler: حتی درک مشترکی از «Spec» و تفاوتش با instruction file وجود ندارد.

⚠️ آبشار برای عامل‌ها

Spec سنگین و فرم‌های زیاد = از دست رفتن چابکی. سبک شروع کنید.

⚠️ رانش Spec (Drift)

Spec-first بدون به‌روزرسانی ← Spec دروغ می‌گوید. فیچرهای مهم را anchored کنید.

⚠️ BRD داخل Rules

context شلوغ، قوانین مبهم، هزینه توکن بالا، کیفیت پایین.

برای اعتبار ارائه، نقدها را هم بگوییم. Böckeler صریحاً هشدار می‌دهد که SDD هنوز در حال شکل‌گیری است. کاربرانی هم گفته‌اند Spec Kit شبیه آبشار است. راه‌حل: سبک شروع کنید و فقط برای فیچرهای مهم سنگین‌تر شوید.
04

تیم از A تا Z

کسب‌وکار ← PO ← Tech Lead ← Developer ← Tester — هر نقش با عامل‌ها

حالا ببینیم این مفاهیم در جریان واقعی تیم چطور به کار می‌روند.

جریان کامل: از نیازمندی تا تست

هر نقش یک artifact تولید می‌کند که ورودی نقش بعدی است. کسب‌وکار مستند دامنه، PO Spec، Tech Lead Plan و Rule و Skill، Developer با عامل کد و PR، و Tester با عامل تست‌ها را از معیار پذیرش می‌سازد.

PO و Tech Lead با عامل‌ها چه می‌کنند؟

Product Owner

  • تبدیل BRD به داستان کاربر با کمک عامل
  • درخواست از عامل: «معیار پذیرش Given/When/Then و لبه‌ها را پیشنهاد بده»
  • اتصال MCP به Jira: ساخت تیکت از Spec
  • بررسی Spec از نظر ابهام و تناقض
  • خروجی: spec.md تأییدشده

Tech Lead

  • مالک AGENTS.md، Rules، Constitution
  • ساخت و نگهداری Skills تیم
  • تأیید Plan و تقسیم Tasks
  • طراحی Harness: تست معماری، Hook، CI
  • تعیین سطح خودمختاری عامل برای هر نوع کار
  • خروجی: plan.md + rules + skills
نقش Tech Lead در دنیای عامل‌ها مهم‌تر می‌شود: او طراح Harness است. هر بار عامل خطای تکراری کرد، Tech Lead یک Rule یا Skill یا تست اضافه می‌کند.

Developer و Tester با عامل‌ها چه می‌کنند؟

Developer

  • Explore: «با subagent بررسی کن follow-up فعلی چطور کار می‌کند»
  • Plan: Plan Mode، فایل‌ها و ترتیب را تأیید کن
  • Implement: با Skill dotnet-cqrs-feature
  • Verify: build + test تا سبز شدن
  • Review: subagent بازبین read-only قبل از PR
  • مالک نهایی کد = انسان

Tester / QA

  • تبدیل معیار پذیرش Spec به test case
  • تولید تست integration / E2E با عامل
  • درخواست: «لبه‌هایی که Spec پوشش نداده را پیدا کن»
  • عامل مرورگر برای تست UI
  • گزارش شکاف Spec به PO
  • خروجی: PASS/FAIL در برابر AC
Developer از «تایپ کردن» به «هدایت و بازبینی» می‌رود. Tester از معیارهای پذیرش Spec مستقیماً تست می‌سازد؛ این همان حسگر Harness است.

الگوی ارکستراسیون عامل‌ها

  • Orchestrator خودش کد نمی‌نویسد؛ تقسیم می‌کند
  • هر متخصص context و ابزار محدود دارد
  • کار موازی در git worktree جدا
  • Reviewer و Explorer فقط خواندنی
  • حداکثر ۳ دور اصلاح، بعد ارجاع به انسان
این الگو در Cursor با subagent ها و best-of-n، در Claude Code با subagent و agent teams، و در ابزارهایی مثل Devin پیاده می‌شود. کلید: نقش‌های جدا با context جدا و تحویل‌های صریح.

Privacy mode، عدم ارسال secret، بررسی سیاست داده هر ابزار، محدودیت دسترسی MCP و ترمینال.

توهم (Hallucination)؟

با context درست، تست قطعی، و بازبینی کاهش می‌یابد — حذف نمی‌شود.

جونیورها چطور یاد بگیرند؟

از عامل «توضیح» بخواهند، Plan را بخوانند، و کد را خودشان review کنند؛ نه فقط accept.

کدام مدل؟

مدل قوی برای Plan و کار سخت؛ مدل سریع/ارزان برای کار تکراری. Harness مهم‌تر از مدل است.

FAQ کامل‌تر با بیش از ۱۵ سؤال در Handbook هست.
