# چگونه یک Spec خوب بنویسیم

## قالب حداقلی
1. هدف (یک پاراگراف)
2. داستان‌های کاربر
3. معیار پذیرش قابل‌تست (Given/When/Then یا چک‌لیست)
4. خارج از محدوده
5. قوانین دامنه مرتبط (لینک یا نقل کوتاه از docs)
6. لبه‌ها و خطاها
7. وابستگی‌ها
8. Definition of Done

## چک‌لیست کیفیت
- [ ] هر معیار پذیرش با تست یا دمو قابل اثبات است
- [ ] معماری بلند اینجا نیست (برود در Plan/ADR)
- [ ] به اندازه یک PR یا اپیک کوتاه است
- [ ] واژه‌ها با glossary کسب‌وکار یکی است
- [ ] Non-goals روشن است (جلوگیری از scope creep عامل)

## مالکیت
- می‌نویسد: PO + Tech Lead
- مصرف می‌کند: Developer agent + Tester
- بعد از اتمام فیچر مهم: Spec را نگه دارید (spec-anchored) تا نگهداری آسان شود
