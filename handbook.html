۱. چرا الان؟ داده‌ها و پارادوکس بهره‌وری

ابزارهای کدنویسی با هوش مصنوعی در چند سال اخیر چهار نسل را پشت سر گذاشته‌اند: تکمیل خودکار (یک خط یا یک تابع)، چت‌بات (پرسش و پاسخ و کپی‌پیست)، عامل (Agent؛ خودش فایل می‌خواند، ویرایش می‌کند، ترمینال و تست اجرا می‌کند) و اکنون تیم عامل‌ها (یک هماهنگ‌کننده و چند عامل متخصص).

۲.۲ حلقه عامل

عامل در یک حلقه کار می‌کند: هدف را دریافت می‌کند، برنامه می‌ریزد، ابزار اجرا می‌کند (خواندن/جستجو/ویرایش فایل، ترمینال، تست، مرورگر)، نتیجه را مشاهده می‌کند و تا رسیدن به هدف تکرار می‌کند.

هشدار: اگر معیار موفقیت قطعی (تست، build، lint) ندهید، عامل خودش به کار خودش نمره می‌دهد. ارزیابی خود مدل از «تمام شد» کم‌اعتمادترین سیگنال در حلقه است؛ نتیجه تست قابل‌اعتمادترین.

۲.۲ب Context چیست؟ (تعریف ساده)

Context = همه اطلاعاتی که مدل همین لحظه می‌تواند ببیند و بر اساس آن‌ها تصمیم بگیرد یا کد بنویسد.

اجزای رایج Context در یک جلسه عامل:

  • پرامپت / هدف شما
  • Rules (مثل AGENTS.md)
  • Skill و Spec فعال‌شده
  • فایل‌هایی که عامل خوانده (کد، docs، diff)
  • تاریخچه همین گفتگو
  • خروجی ابزارها (تست، build، MCP)

Context Window ظرفیت محدود این «میز کار» است. وقتی پر شود، بخش‌هایی از اطلاعات قدیم یا کم‌اولویت ممکن است از دسترس خارج شوند. به همین دلیل context شلوغ یا بی‌ربط کیفیت را پایین می‌آورد. کار تیم این است که محتوای باارزش را عمداً روی میز نگه دارد و بقیه را بیرون بگذارد، این همان مهندسی زمینه است.

۲.۳ مهندسی زمینه (Context Engineering)

«Context engineering یعنی گزینش آنچه مدل می‌بیند، تا نتیجه بهتری بگیرید.»، Bharani Subramaniam، در مقاله «Context Engineering for Coding Agents» نوشته Birgitta Böckeler، martinfowler.com، فوریه ۲۰۲۶

پنجره context محدود است و هر چیز بی‌ربط کیفیت را پایین می‌آورد. ابزارهای پیکربندی context در عامل‌ها:

  • Rules دستورالعمل‌های دائمی پروژه (همیشه یا با الگوی مسیر بارگذاری می‌شوند)
  • Skills رویه‌هایی که فقط هنگام نیاز بارگذاری می‌شوند
  • Specs قرارداد فیچر در حال ساخت
  • MCP اتصال به سیستم‌های بیرونی (Jira، GitLab، دیتابیس، مستندات، مرورگر)
  • Subagents عامل‌های کمکی با context جداگانه
  • خود کدبیس، Böckeler تأکید می‌کند که طراحی کد هم بخشی از context است؛ کد تمیز و یکدست، خروجی بهتر عامل.

۲.۴ مهار (Harness): راهنماها و حسگرها

در مقاله «Harness engineering for coding agent users» در martinfowler.com، Harness هر چیزی در عامل است جز خود مدل. Harness بیرونی که ما می‌سازیم دو هدف دارد: بالا بردن احتمال درست انجام دادن کار در بار اول، و ایجاد حلقه بازخوردی که تا حد ممکن خطاها را قبل از رسیدن به انسان اصلاح کند.

راهنماها (Guides)، قبل از عمل

  • AGENTS.md و Rules
  • Spec و معیار پذیرش
  • Skills
  • ADR و اسناد معماری
  • نمونه کد خوب در ریپو

حسگرها (Sensors)، بعد از عمل

  • Build / Compiler
  • Unit و Integration Test
  • Linter و Formatter
  • تست‌های معماری (مثلاً NetArchTest)
  • عامل بازبین read-only

۲.۵ MCP، Subagent و Hook

  • MCP (Model Context Protocol): پروتکل استاندارد برای اتصال عامل به ابزارها و داده‌های بیرونی.
  • Subagent: عامل کمکی با context و ابزارهای محدود خودش که فقط خلاصه نتیجه را برمی‌گرداند. برای تحقیق در کدبیس (تا context اصلی آلوده نشود) و بازبینی بی‌طرف عالی است.
  • Hook: اسکریپت قطعی که در رویدادهای چرخه عامل اجرا می‌شود (قبل/بعد از ابزار، پایان کار). Anthropic: «برخلاف دستورالعمل‌های CLAUDE.md که توصیه‌ای هستند، Hook ها قطعی‌اند و تضمین می‌کنند کار انجام شود.»

مهم‌ترین مفهوم این راهنما: این چهار مورد چیزهای متفاوتی هستند و قاطی کردن آن‌ها رایج‌ترین اشتباه تیم‌هاست.

۳.۱ Spec چیست؟

Spec قرارداد بین کسب‌وکار، تیم فنی و عامل است، قبل از نوشتن کد. در محل specs/NNN-feature/spec.md قرار می‌گیرد، در git نسخه‌بندی می‌شود و در PR بازبینی می‌شود. مهم‌ترین بخش آن معیار پذیرش قابل تست است؛ همین معیارها بعداً تست می‌شوند و حسگر عامل را تشکیل می‌دهند.

۳.۲ Rule چیست؟

Rule دستورالعمل دائمی است که عامل در تقریباً هر ویرایش مرتبط رعایت می‌کند. چون Rule ها همیشه (یا با هر فایل منطبق) در context بارگذاری می‌شوند، هر کلمه اضافه هزینه دائمی دارد. پس کوتاه، دستوری و دائمی بنویسید. محل‌ها: AGENTS.md، .cursor/rules/*.mdc، CLAUDE.md، .github/copilot-instructions.md.

۳.۳ Skill چیست؟

Skill یک پوشه با فایل SKILL.md است (استاندارد باز agentskills.io که اصالتاً توسط Anthropic ساخته شد و اکنون Cursor، Claude Code، GitHub Copilot و Codex پشتیبانی می‌کنند). فایل شامل frontmatter با name و description و بدنه دستورالعمل است و می‌تواند پوشه‌های اختیاری scripts/، references/ و assets/ داشته باشد.

بارگذاری تدریجی (Progressive Disclosure)

  1. کشف: در شروع فقط name و description همه Skill ها (~۱۰۰ توکن هرکدام)
  2. فعال‌سازی: وقتی کار با description جور شد، کل SKILL.md (توصیه: کمتر از ۵۰۰۰ توکن)
  3. اجرا: فایل‌های references/scripts فقط در صورت نیاز

به همین دلیل می‌توانید ده‌ها Skill داشته باشید بدون اینکه context شلوغ شود. فیلد description تمام بار تشخیص «کی فعال شود» را به دوش می‌کشد.

۳.۴ مستندات کسب‌وکار، و چرا «قانون کسب‌وکار» ≠ Rule عامل

این پرتکرارترین سؤال است: «قوانین کسب‌وکار ما Rule هستند یا Skill یا سند؟»

مثال: «اقساط معوق بیش از ۳۰ روز باید پیگیری شوند.»

  • ✓ در مستند دامنه (docs/domain/installments.md)، حقیقت برای انسان‌ها
  • ✓ در Spec فیچر مربوط، به‌شکل معیار پذیرش Given/When/Then
  • ✓ اختیاری: در references/ یک Skill، اگر عامل‌ها مکرر به واژه‌نامه دامنه نیاز دارند
  • ✗ در .cursor/rules یا AGENTS.md، مگر اینکه قرارداد دائمی کدنویسی باشد، مثل «فیلدهای پولی همیشه decimal»

۴. توسعه مبتنی بر Spec، دیدگاه martinfowler.com

مرجع اصلی این فصل مقاله «Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl» نوشته Birgitta Böckeler (Distinguished Engineer در Thoughtworks) در سایت Martin Fowler است، به‌همراه پادکست Thoughtworks با حضور او و Laura Tacho.

۴.۱ مسئله: Vibe Coding

«Vibe coding» یعنی پرامپت ← کد ← امید. برای نمونه‌سازی سریع خوب است، اما در محصول مشکل اصلی هم‌راستایی است: عامل ممکن است چیز اشتباهی را کاملاً درست بسازد. Laura Tacho (DX) در پادکست می‌گوید طبق داده‌هایشان مشکل پایدار تیم‌ها کمبود هم‌راستایی است و SDD تلاشی برای حل بخشی از همین است.

۴.۲ تعریف Böckeler

SDD یک گردش‌کار است برای ایجاد Spec خوش‌فکرشده در فرایند برنامه‌ریزی، قبل از پیاده‌سازی، که سپس به عامل تحویل داده می‌شود. ارزش کلیدی آن هم‌راستایی و همگام نگه داشتن Spec با کد است.

نتیجه‌گیری اصلی او: «مثل هر مفهوم نوظهور، اصطلاحات هنوز بسیار سیال است و spec-driven می‌تواند معانی مختلفی داشته باشد. حتی درک مشترکی از اینکه Spec چیست و چه تفاوتی با instruction file یا پرامپت دارد وجود ندارد.»

۴.۴ سه ابزار از نگاه Böckeler

  • Kiro (AWS): ساده‌ترین و سبک‌ترین؛ جریان Requirements ← Design ← Tasks. عمدتاً spec-first.
  • Spec Kit (GitHub): به‌صورت CLI توزیع می‌شود و ساختار workspace را برای طیف وسیعی از دستیارها می‌سازد؛ تعامل با slash command. «چون همه artifact ها در workspace شما قرار می‌گیرند، این سفارشی‌پذیرترین ابزار از این سه است.» با این حال در عمل spec-first است.
  • Tessl: تنها ابزاری که صریحاً به سمت spec-anchored و حتی spec-as-source می‌رود. کد تولیدی با کامنت // GENERATED FROM SPEC - DO NOT EDIT علامت می‌خورد؛ فعلاً نگاشت ۱:۱ بین Spec و فایل. هنوز beta است.

۴.۶ SDD چطور به تیم ما کمک می‌کند

  1. هم‌راستایی زودهنگام: PO و Tech Lead قبل از مصرف توکن و وقت توسعه توافق می‌کنند.
  2. دروازه کیفیت: معیار پذیرش ← تست ← حسگر خودکار عامل.
  3. کاهش دوباره‌کاری: کمتر «عامل چیز اشتباهی ساخت».
  4. تحویل صریح بین نقش‌ها: BRD ← Spec ← Plan ← Tasks ← کد ← تست.
  5. بازبینی بهتر: بازبین در برابر Spec چک می‌کند، نه حافظه یا حدس.
  6. رشد جونیورها: Spec بریف کار است و Skill روش انجام.
  7. حافظه سازمانی: چرا یک فیچر این‌طور ساخته شد، در ریپو می‌ماند، نه در تاریخچه چت.

۴.۷ نقدها و هشدارها

  • اصطلاحات سیال: «Spec» برای افراد مختلف معانی متفاوت دارد؛ در تیم تعریف مشترک بگذارید (همین فصل ۳).
  • آبشار برای عامل‌ها: برخی کاربران Spec Kit را «waterfall برای عامل‌ها» و بیش از حد سنگین توصیف کرده‌اند. Spec را سبک و اندازه یک PR نگه دارید.
  • رانش (Drift): در spec-first اگر Spec به‌روز نشود، بعداً گمراه‌کننده است. برای فیچرهای مهم spec-anchored.
  • Spec جای فکر کردن را نمی‌گیرد: فرم Spec به‌تنهایی پرامپت بهتر نمی‌سازد؛ تنظیمات خاص پروژه (ابزار، محیط) را هم باید صریح بنویسید.

۵.۱ نوشتن Spec

قالب حداقلی

  1. هدف، یک پاراگراف درباره نتیجه

چک‌لیست کیفیت

  • ☐ معماری مفصل اینجا نیست (برود در plan.md یا ADR)
  • ☐ اندازه یک PR یا اپیک کوتاه است

۵.۲ نوشتن Rule

چه چیزی Rule باشد

  • مرزهای معماری (Clean Architecture)
  • قراردادهای نام‌گذاری و پوشه
  • حداقل‌های تست
  • لیست «هرگز» امنیتی
  • دستورهای build/test که عامل باید اجرا کند

ویژگی‌های Rule خوب و بد

✓ خوب

  • کوتاه و دستوری (Do / Don't)
  • دائمی
  • با globs محدود
  • چند فایل کوچک به‌جای یک فایل غول
  • مالک مشخص، review مثل کد

✗ بد

  • مقاله یا آموزش بلند (← Skill)
  • دستور مخصوص یک فیچر (← Spec)
  • کپی BRD (← docs)
  • تکرار محتوای AGENTS.md در هر فایل ابزار

فرمت .mdc در Cursor

---
description: Clean Architecture boundaries for .NET projects
globs: "**/*.{cs,csproj}"
alwaysApply: false
---
# .NET Clean Architecture
## Do
- Depend inward (Host → Application → Domain).
## Don't
- Don't reference Infrastructure from Domain.

Cursor تنها فرمتی است که فعال‌سازی جداگانه برای هر Rule دارد: همیشه (alwaysApply: true)، با الگوی فایل (globs)، به تشخیص عامل (با description) یا دستی. فایل قدیمی .cursorrules منسوخ است.

ساختار

قواعد frontmatter

چک‌لیست

۶.۳ الگوهای ارکستراسیون

  • Orchestrator + متخصص‌ها: یک عامل هماهنگ‌کننده که خودش کد نمی‌نویسد، کار را بین Explorer (read-only)، Implementer، Tester و Reviewer (read-only) تقسیم می‌کند.
  • Context جدا: هر subagent context و ابزار محدود خودش را دارد و فقط خلاصه برمی‌گرداند.
  • کار موازی در git worktree: هر Implementer در یک worktree/branch جدا.
  • دروازه‌های انسانی: تأیید Plan و تأیید Merge.
  • سقف تکرار: مثلاً حداکثر ۳ دور اصلاح برای هر تسک، سپس ارجاع به انسان.
  • PR عامل = PR انسان: همان CI، branch protection و بازبینی.

۸. چطور با عامل صحبت کنیم + ضدالگوها

۸.۱ آناتومی پرامپت خوب

  1. هدف: چه نتیجه‌ای؟ (نه فقط «درستش کن»)
  2. Context: Spec، فایل‌های مرتبط، کد مشابه موجود، تیکت
  3. محدودیت‌ها: چه چیزی تغییر نکند، Non-goals، الگوی موجود
  4. تأیید: چطور بفهمیم درست است؟ تست، build، معیار پذیرش
  5. خروجی: Plan؟ PR؟ خلاصه؟ قالب مشخص
  6. حالت: اول Plan Mode، بعد اجرا

قاعده Anthropic: اگر diff را می‌توانید در یک جمله توصیف کنید، Plan لازم نیست؛ وگرنه اول Explore و Plan.

۸.۲ مثال

✗ بد: «یه API برای پیگیری اقساط بنویس.»
✓ خوب:

۱. اول با subagent بررسی کن InstallmentService فعلی چطور کار می‌کند.
۲. در Plan Mode فایل‌ها و ترتیب را پیشنهاد بده و صبر کن تا تأیید کنم.
۳. از Skill dotnet-cqrs-feature پیروی کن.
۴. به Domain و جدول‌های موجود دست نزن؛ ارسال پیامک خارج از محدوده است.
۵. هر معیار پذیرش ۱ تا ۴ باید یک unit test داشته باشد؛ dotnet test سبز.
۶. در پایان خلاصه تغییرات و نگاشت معیار پذیرش به تست بده.

۸.۳ ترفندهای کاربردی

  • برای هر تسک یک جلسه/چت تازه؛ context طولانی کیفیت را پایین می‌آورد.
  • از عامل بخواهید قبل از کد سؤال‌های روشن‌کننده بپرسد.
  • «این کارها موازی قابل انجام‌اند» را صریح بگویید.
  • برای بازبینی بی‌طرف: «از subagent ای استفاده کن که گفتگوی قبلی ما را ندیده.»
  • قالب خروجی را مشخص کنید (جدول، چک‌لیست، نگاشت AC به تست).

۱۰. پرسش‌های پرتکرار (FAQ)

۱. آیا AI جای توسعه‌دهندگان را می‌گیرد؟

نقش را تغییر می‌دهد، نه حذف. تمرکز از تایپ کد به طراحی، نوشتن Spec، ساخت Harness و بازبینی می‌رود. مسئولیت و مالکیت کد با انسان است.

۲. قوانین کسب‌وکار Rule هستند یا Skill یا Spec؟

معمولاً هیچ‌کدام از Rule و Skill. جای اصلی‌شان مستندات دامنه است و در هر فیچر به‌شکل معیار پذیرش در Spec می‌آیند. Rule فقط برای قراردادهای دائمی کدنویسی است.

۳. BRD را داخل AGENTS.md بگذاریم؟

خیر. BRD در docs/؛ خلاصه قابل تست مربوط به هر فیچر در Spec. AGENTS.md باید کوتاه بماند.

۴. Spec-first یا spec-anchored؟

با spec-first شروع کنید. برای ماژول‌های اصلی و پرتغییر، Spec را بعد از merge نگه دارید و با هر تغییر به‌روز کنید (spec-anchored). Spec-as-source فعلاً آزمایشی است.

۵. چه کسی مالک Spec، Rule و Skill است؟

Spec: PO + Tech Lead. Rule: Tech Lead. Skill: Tech Lead و توسعه‌دهندگان ارشد. Doc: PO/تحلیلگر. همه در git و با PR بازبینی می‌شوند.

۶. Spec Kit یا Kiro یا دستی؟

اگر ابزار فعلی‌تان Cursor/Copilot/Claude است، Spec Kit چون روی همان ابزار کار می‌کند. Kiro اگر IDE جدید می‌پذیرید. برای شروع، قالب ساده WRITE-A-SPEC.md همین ریپو کافی است.

۷. امنیت کد شرکت چه می‌شود؟

Privacy mode ابزارها را فعال کنید، سیاست نگهداری داده هر ارائه‌دهنده را بررسی کنید، secret را هرگز در پرامپت/Rule نگذارید، دسترسی MCP و ترمینال را محدود کنید و برای اسکن secret از Hook یا CI استفاده کنید.

۸. هزینه چقدر است؟

قیمت پایه ۱۰ تا ۲۰ دلار ماهانه، ولی مصرف عامل با credit محاسبه می‌شود. مدل سنگین را برای Plan و کار سخت، و مدل سریع را برای کارهای تکراری استفاده کنید.

۹. PR های تولید عامل را چطور بازبینی کنیم؟

دقیقاً مثل PR انسانی: همان CI و branch protection. در برابر Spec چک کنید. قبل از PR یک subagent بازبین read-only اجرا شود. PR ها را کوچک نگه دارید.

۱۰. جونیورها چطور یاد بگیرند و وابسته نشوند؟

از عامل «توضیح» بخواهند، Plan را قبل از اجرا بخوانند و نقد کنند، و کد را خودشان review کنند. Spec و Skill راهنمای ساختاریافته برایشان است.

۱۱. با توهم (hallucination) چه کنیم؟

با context درست (Spec، Rule)، حسگرهای قطعی (تست، build) و بازبینی کاهش می‌یابد ولی صفر نمی‌شود. API ها و پکیج‌های پیشنهادی را تأیید کنید.

۱۲. کدام مدل بهتر است؟

مدل‌ها مرتب عوض می‌شوند. مدل قوی برای برنامه‌ریزی و استدلال، مدل سریع برای کارهای ساده. Harness خوب از مدل بهتر مهم‌تر است.

۱۳. چند ابزار هم‌زمان؟ ناسازگار نمی‌شوند؟

با AGENTS.md به‌عنوان منبع اصلی و فایل‌های مخصوص ابزار کوتاه و ارجاع‌دهنده، و Skills در .agents/skills، همه ابزارها یک قانون را می‌خوانند.

۱۴. Rule چقدر باید طولانی باشد؟

تا حد ممکن کوتاه. اگر بیش از یک صفحه شد، بخش‌های رویه‌ای را به Skill و توضیحات دامنه را به docs منتقل کنید.

۱۵. Hook چه فرقی با Rule دارد؟

Rule توصیه است و مدل ممکن است فراموش کند؛ Hook اسکریپت قطعی است و همیشه اجرا می‌شود. هر چیزی که «حتماً» باید اتفاق بیفتد را Hook کنید.

۱۶. Subagent کی لازم است؟

وقتی کار خواندن زیاد دارد (تحقیق کدبیس)، وقتی ارزیابی بی‌طرف می‌خواهید (بازبینی)، یا وقتی کارهای مستقل موازی دارید.

۱۷. کد legacy شلوغ داریم؛ عامل کمکی می‌کند؟

بله ولی با احتیاط: اول تست‌های characterization با عامل بسازید، بعد refactor. کد بی‌نظم context بدی است؛ Böckeler بر «طراحی کدبیس دوستدار AI» تأکید دارد.

۱۸. از کجا شروع کنیم؟

همین هفته: یک AGENTS.md کوتاه برای یک سرویس، استفاده از Plan Mode برای یک تسک واقعی، و نوشتن یک Spec با قالب این ریپو.

# AGENTS.md، .NET Clean Architecture

## Project overview
- Stack: .NET / C#, Clean Architecture (Domain / Application / Infrastructure / Host)
- Patterns: CQRS with MediatR, FluentValidation, Result pattern
- Tests: xUnit + NSubstitute

## Commands
dotnet build
dotnet test
dotnet format

## Architecture rules (always)
- Domain must not depend on Infrastructure or Host.
- Keep controllers thin; business logic in Handlers/Services.
- Money fields: decimal only، never double/float.
- Never hardcode secrets, tokens, or connection strings.
- For a new feature, read specs/ first; no code without acceptance criteria.

## Definition of Done
1. Build green  2. Related tests pass
3. Spec acceptance criteria covered  4. No secrets in diff

name: ef-migration
description: Create and apply EF Core migrations safely in a .NET project.
  Use when the user asks for a database migration or schema change.
---
## Steps
1. Confirm entity/config changes are in the Infrastructure project.
2. dotnet ef migrations add <Name> --project <Infra> --startup-project <Host>
3. Review migration for destructive changes.
4. Apply locally only if asked.
5. dotnet build + tests.
## Never
- Never invent connection strings.
- Never drop production data without explicit human approval.
